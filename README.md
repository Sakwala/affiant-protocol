# affiant-protocol

The rulebook for [Affiant](https://affiant.dev): the wire format, the numbered invariants and the conformance fixtures that every Affiant implementation — in any language — must satisfy.

**[Implement Affiant in your language →](IMPLEMENTING.md)** — how a new implementation, in any language and under its own name, becomes a conforming one.

Affiant turns every database write an LLM agent proposes into an **Affidavit**: a per-field evidence record (the value, the previous value, where each value came from, how confident) filed in a **Docket** and shown as an **Evidence Card** that a person approves, amends or rejects before the host writes. A **Standing Order** is a policy verdict that approves a write with no person present.

This repository holds no runtime code. It holds:

- `schemas/` — JSON Schema for the wire format: the designed protocol in [`schemas/0.1.0/`](schemas/0.1.0/) (the Affidavit, the field, provenance and bindings, the Docket entry, the attestation, the envelopes, the registries), and the frozen `0.0.1-seed` description of the shipped .NET wire beside it
- `INVARIANTS.md` — the numbered, testable rules an implementation must enforce
- `conformance/` — the fixtures, the runner specification, the driver contract and the parity-manifest format, and from v0.2.0 the [adapter fixtures](conformance/ADAPTER-RUNNER.md) and the [adapter claims lint](conformance/ADAPTER-CLAIMS.md) that check the three rules about an adapter's seam

`schemas/`, `INVARIANTS.md` and the whole of `conformance/` — the fixtures, the runner specification, the driver contract and the parity-manifest format — are tagged `v0.2.0`, and both drivers have published a parity manifest here at that tag, both with an empty failing set: the TypeScript reference implementation's, over all 80 documents — the 68 of the `conformance` section and the 12 of the `adapter` one, which it is the only implementation to run — and the .NET implementation's, now at NuGet package `1.0.0-beta.3.1`, over the 68, declaring no adapter and so running none of the `adapter` section.

Versions are git tags. Each implementation pins a tag and bumps it in its own pull request; a parity manifest records, per implementation, which fixtures it does not yet pass — in public, checked in CI.

- 2026-09-08 — **`v0.1.3`: PV-3 says who establishes presence — the implementation, from the utterance.** The rule's parenthetical read "the value is literally present in the utterance; with an `utterance-span` binding when the inference port supplies offsets", which left the grade in the inference port's hands. No shipped port asks a model for `presence` at all, so both implementations fell through to `Inferred` and every value a person typed in chat was sworn **"AI suggested"** on the Evidence Card ([`Sakwala/affiant#123`](https://github.com/Sakwala/affiant/issues/123)). PV-3 now states the condition itself: the implementation finds the value text in the unmodified turn — ordinal, folding ASCII case and nothing else, with neighbours that are absent or are none of a letter, a mark, a decimal digit or connector punctuation — grades `Conversation` on a hit and `Inferred` otherwise, and binds a hit to `{ offset, length, hash }` over the **utterance's own** substring. The port's `presence` and `utteranceSpan` become hints verified the same way: a `literal` the text does not confirm is `Inferred`, and a value the text does carry is `Conversation` even where the port said nothing. A caller with no utterance in hand keeps the port's report, and no port is asked to change.

  The comparison is pinned so two implementations fold alike without depending on a runtime's Unicode data, which no two of them share — ASCII case only, no culture, no normalisation — the neighbour test covers letters, marks, decimal digits and connector punctuation, a number's value text is SR-1's canonical rendering rather than the port's raw token, a port-supplied span verifies only where it is itself a hit and carries integer-valued coordinates, no hit begins or ends inside a surrogate pair, and a `value` a field cannot carry — `null`, an object, an array, the empty string, a non-finite number — is nothing the port reported at all.

  [`conformance/RUNNER.md`](conformance/RUNNER.md) and [`conformance/fixture.schema.json`](conformance/fixture.schema.json) make both hints optional and say what they are; [`conformance/lint/lint.mjs`](conformance/lint/lint.mjs) runs the finder over every fixture's own utterance and checks every proposed inferred field's expectations against it — the grade, `bound`, and the span where one is pinned. Five fixtures arrive with the amendment, **authored here rather than promoted**, because neither implementation had the behaviour to copy. Four are its negative oracle against `1.0.0-beta.3` ([`conformance/ORACLE.md`](conformance/ORACLE.md)): [`gate/inference-presence-computed-from-the-utterance`](conformance/fixtures/gate/18-inference-presence-computed-from-the-utterance.json), [`gate/inference-port-literal-unconfirmed`](conformance/fixtures/gate/19-inference-port-literal-unconfirmed.json), [`gate/inference-port-span-fails-the-boundary`](conformance/fixtures/gate/20-inference-port-span-fails-the-boundary.json) and [`gate/inference-case-folds-and-the-digest-is-the-utterances`](conformance/fixtures/gate/21-inference-case-folds-and-the-digest-is-the-utterances.json). The fifth, [`gate/inference-empty-value-is-nothing-reported`](conformance/fixtures/gate/22-inference-empty-value-is-nothing-reported.json), pins the other half of the rule — a `value` that is `null`, an object, an array or the empty string is **nothing reported**, so nothing is merged and the field stays `Empty` — and is on no oracle list, because `1.0.0-beta.3` already skips an empty value and passes it.

  Three things changed beyond the rule. The fixture schema, twice: `presence` left the required keys, and `fieldMatcher` gained an optional `utteranceSpan` so a fixture can pin a binding's offset, length and digest — nothing in the suite could state that before, which is why "the first hit wins" and "the digest is the utterance's own bytes" had no coverage. And one existing fixture: [`sequence-a/picker-external-binding`](conformance/fixtures/sequence-a/04-picker-external-binding.json) scripted `presence: "literal"` with no span over an utterance that carries `Active`, so from `v0.1.3` its `status` is bound to the span it was read from, and it joins the beta.3 oracle list. And the parity manifest's `runtimes[]` gained a `unicodeVersion` — optional in the schema, required by the lint of every manifest read at `v0.1.3` or later — because the neighbour test reads its categories from a runtime's own Unicode database and two runtimes need not carry the same one. No wire shape and no canonical vector changed.

Both published runs read at `v0.1.2`, where it was 63, and both are expected to fail the four oracle fixtures and the amended one until each implementation lands the change; on the fifth the two shipped implementations already differ — .NET skips a port's empty value and passes it, the TypeScript core admits it as `Inferred` and does not; the parity manifests move when they re-pin, and the tag and the "current tag" lines move with the release commit.

- 2026-09-04 — **`v0.1.2` is tagged: SR-1 states what the canonical form is taken over, and two pinned hashes move.** The
  form is over the **Affidavit as [`schemas/0.1.0/affidavit.schema.json`](schemas/0.1.0/affidavit.schema.json) defines

  presentation is **not** in it: `allowedValues`, `pattern`, `warnings` and `requiresConfirmation` are a host's rendering
  of a proposal rather than its sworn substance, and a rendering decision inside a hash a grant is checked against would
  let restyling an input invalidate a grant minted over evidence that did not change. The seven canonical vectors already
  stated both halves — every one's `expectedBytesUtf8` carries `protocolVersion`, and none carries a presentation key — so
  no vector, schema or wire changed here.

  What was wrong was the **reference implementation's runtime form**, not this text. Its Affidavit model omitted
  `protocolVersion` and its wire writer added it on the way out, so the bytes a Docket row's `canonicalHash` was taken
  over — the bytes a host's execution grant binds to — were not the bytes of the same record on a card. Two declarative
  fixtures pinned a hash produced by that path and are re-promoted from the corrected reference:
  [`sequence-a/approve-round-trip`](conformance/fixtures/sequence-a/01-approve-round-trip.json)
  `776b7b40…6837275` → `2ce4c4af…840eca9` and
  [`decide/amend-recompute`](conformance/fixtures/decide/06-amend-recompute.json)
  `8d1579d7…4ecff6a` → `d389401d…3bd3402`. The corrected bytes are the previous bytes with one key inserted. Those two
  values are the only ones that moved.

  An earlier draft of this amendment said the opposite — that `protocolVersion` was envelope-only and absent from the
  canonical form — and was **not** made, because the vectors refuse it. This entry replaces that note. The same commit's
  GT-4 amendment stands unchanged: GT-4 already said entry ids are "derived deterministically from the tenant, the
  conversation, the tool and the canonical form of the operation and its arguments", and a **Derivation** paragraph states
  exactly what that means — the canonical-JSON material (`tenantId`, `conversationId`, `toolName`, `operation`, `args`,
  and `supersedes` present only on a resubmission), the SHA-256 digest over its UTF-8 bytes, and the RFC 9562 UUIDv8
  layout — matching the reference implementation's `deriveEntryId` (`Sakwala/affiant-ts`
  `packages/core/src/gate/pipeline.ts`), and why the id's material is not the Affidavit's own canonical form (SR-1): the
  id must be fixed before inference runs, and inference is not deterministic.

CV-5 is a lint rather than a fixture, because no fixture can observe a statement about documentation and packaging: [`conformance/lint/adapter-claims.mjs`](conformance/lint/adapter-claims.mjs) reads an adapter package's declared durability claims and its README against the runtime's published dist-tags ([`conformance/ADAPTER-CLAIMS.md`](conformance/ADAPTER-CLAIMS.md)), and this repository's CI runs it against a corpus of its own on every push, because a lint cited as a rule's coverage and never executed is not coverage. The three exemptions that read `until: "0.2.0"` are gone.

Next: the items now reserved for v0.3 and later — the PROV-O attestation export, `MultiParty` and referral semantics, the queued-inference fixture for AZ-6, and PV-2's `binding` promoted from SHOULD to MUST. Follow progress in [Discussions](https://github.com/Sakwala/affiant-protocol/discussions) and the [Affiant roadmap](https://github.com/Sakwala/affiant/blob/main/ROADMAP.md).
